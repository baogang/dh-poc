# 下一阶段事项办理回归集（road-v4）

此集合补充 road-v3 的 34 个业务/FAQ/情绪分流案例，专门测试草稿、更正、恢复、核对和时间线。15 条均为合成 MOCK 对话，可重复执行，不含真实个人资料。不得把本集合通过率解释为线上准确率或独立盲测结果。

原有 road-v1/v2/v3 的原始案例保持不变；v1/v2 包含已退役的策略，只用于历史比较。当前发布门槛为 road-v3 全集与 road-v4 全集一起通过。

## 数据格式与执行

机器数据见 [cases.jsonl](cases.jsonl)。每行一个案例，含 `id/title/login/actions/expected`。`actions` 是用户对话、界面点击和测试故障；`expected` 是独立判分标签，不提供给 DeepSeek。`login` 只使用 demo、demo-no-address、demo-other，模拟密码均为 demo。

```sh
npm test
npm run test:mocks
npm run road:test:postgres
npm run eval:offline
npm run road:eval -- --split all
npm run road:matters-eval
npm run road:emotion-eval -- --split all
npm run road:knowledge-audit
npm run check
```

真实模型评测需要本机已有的 DeepSeek 配置。Neon 测试自动创建独立临时 schema，完成后清理，不覆盖线上账号数据。业务与事项模型案例每条使用独立内存仓库；同一案例内部的新会话共享该案例的模拟账号数据，以准确测试恢复而避免案例串扰。

结果写入被 Git 忽略的 `reports/road/`，最终脱敏摘要写入 `docs/evaluation/road-next-validation-20261019.json`。

## 手工验收步骤

开始前选择中文或 English，取消勾选“显示任务列表”，确认以下所有关键操作仍能在聊天中完成。每条独立测试建议使用独立本机数据；线上三个模拟账号各自共享事项，已有数据不会因“新对话”而重置。使用合成地址，勿输入真实居民资料。

| ID | 测什么 | 操作及通过条件 |
|---|---|---|
| DRAFT-01 | 更正地址 | 报告 Riyadh / Test Cedar Road 的坑洞；确认卡点“修改信息”改为 Test Maple Road。旧卡失效，新卡再次确认后只创建一单，地址必须是修改后的值。 |
| DRAFT-02 | 多语种原文 | 中文报单，将地址改为 الرياض / شارع الاختبار。回执保留原拼写，不能翻译或替换地址。 |
| DRAFT-03 | 跨对话恢复 | 确认卡选“保存，稍后继续”；新对话登录同一账号；“我的事项”恢复，重新核对后确认。内容完整，只提交一次。 |
| DRAFT-04 | 恢复不等于批准 | 恢复草稿后停住，不按“确认提交”。业务系统仍没有新增记录。 |
| DRAFT-05 | 多窗口冲突 | 窗口 A 停在确认，窗口 B 登录同一账号并恢复该草稿。A 的旧确认被拒绝，B 确认才可提交。 |
| DRAFT-06 | 跨账号隔离 | 保存草稿后，新会话改登 demo-other。不得看到、恢复或删除原账号草稿。 |
| DRAFT-07 | 删除草稿 | 删除待办草稿；旧恢复请求和旧确认请求均拒绝，不能创建工单。删除在存储中标记 discarded，不抹除审计证据。 |
| DRAFT-09 | 恢复后的反馈归因 | 保存草稿后先查询历史，再恢复原草稿并确认。回答评价应归属于恢复的报单请求，不能错算成历史查询回答。 |
| DRAFT-08 | 无效更正 | 将必填城市/街道或描述清空。保存失败，原来有效的确认卡仍可继续，不能悄悄更改数据。 |
| RECOVERY-01 | 提交后响应丢失 | 测试器注入提交后丢失响应。同一幂等键恢复结果，账户只新增一单、一次变化、一条提醒。 |
| RECOVERY-02 | 提交前接口失败 | 注入连续两次提交前 503。显示结果待核对；先核对为未提交，再重试同一操作，只形成一单。 |
| TIMELINE-01 | 进度及提醒持久化 | 提交后在“我的事项”点两次“演示：推进一个状态”，得到 OPEN → IN_PROGRESS → RESOLVED；标为已读；新对话登录仍保留状态、三条时间线和已读标记。 |
| TIMELINE-02 | 投诉内容更正 | 请求投诉自己的 T102；先查询，再在确认卡修改原因。旧确认失效；最终投诉关联 T102、只含新原因。 |
| TIMELINE-03 | 关闭状态 | 请求关闭自己的 T102；查询、确认后再登录，显示 CLOSED，时间线记录关闭；不能声称道路已修复。 |
| BOUNDARY-01 | 已提交事项修改边界 | 提交后要求改已提交工单地址，同时明确不要另建、关闭、投诉或转人工。不能伪造“已更正”，也不能偷偷调用其他写接口；原记录保持不变。 |

## 判分口径

- 每个案例必须所有检查通过；预期失败（过期确认、跨账号、无效输入）只有被正确拒绝才算通过。
- 工具选择单位为“案例 × 不重复的业务工具类型”。TP = 应选且选中；FP = 不应选却选中；FN = 应选却遗漏。精确率 TP/(TP+FP)，召回率 TP/(TP+FN)，没有分母时记空值。重试次数不增加成功数。
- 草稿恢复中的已知两步计划由宿主从保存的结构化参数恢复，属于 UI/宿主控制，不计作模型自主规划成绩。初始业务请求及更正后的执行仍由 PI 工具循环运行并判分。
- 另查实际工单数量、精确参数、版本校验、逐次写入 HITL、真实回执、时间线、提醒及账号隔离。工具选对不代表业务已经成功。
- 工程测试还覆盖提交后会话保存失败、重启恢复、并发相同键/不同键、多进程 Neon 行锁、隐去演示工具、CSRF、答案反馈证据等非模型边界。
- timeline 的 `reference_id` 来自模拟业务的工单/投诉/人工单编号，状态模拟器则生成明确的 mock-update 引用；不生成缺失的历史受理或完成过程。

## 当前演示边界

草稿从新报单“内容已齐全、准备确认提交”时自动保存，支持修改城市、街道和描述；投诉确认支持修改原因。尚未收齐资料的对话由原会话保存，不属于可跨账号重新登录恢复的草稿。已提交事项没有修改 API，不能用聊天伪装成功。

只有站内演示提醒，没有短信、邮件、推送或真实客服通知。`ROAD_DEMO_UI=false` 时界面和后端均禁用人工推进工单状态。模拟登录仅代表演示账号隔离，不代表真实政府身份认证。账户事务和幂等账本覆盖当前同库 MOCK；接真实外部接口仍需业务方幂等/查询/对账协议，不能据此承诺分布式 exactly-once。
